# Agent Instructions

## Language

All code, comments, and documentation in this repository must be written in English. This applies to every file (scripts, configs, README, this file included) regardless of the language used in the conversation.

## What this repo is

Personal dotfiles managed with [GNU Stow](https://www.gnu.org/software/stow/). Each top-level directory is a Stow package (`zsh/`, `vim/`, `kitty/`, `claude/`, and more added over time). The internal layout of each package mirrors exactly where its files should land under `$HOME` — e.g. `zsh/.config/zsh/.zshrc` symlinks to `~/.config/zsh/.zshrc`, `vim/.vimrc` symlinks to `~/.vimrc`.

Supports two machines with different package sets:
- **Linux**: `zsh`, `vim`, `kitty`, `claude` (more packages added here over time)
- **macOS**: `zsh`, `vim`, `kitty`, `claude`

## Commands

- `./setup.sh link` — symlink the OS-appropriate packages into `$HOME` via `stow`. Installs `stow` first if missing (asks before installing).
- `./setup.sh unlink` — remove those symlinks (`stow -D`).
- `bash -n setup.sh` — syntax-check the setup script without running it.

There is no build/lint/test suite in this repo.

## Architecture notes

- **Package = Stow package**, not an app grouping. A package's directory tree under its root is the literal path that will be symlinked under `$HOME` (Stow's `--target` convention). When adding a new package, create it as `<pkg>/<path-as-it-should-appear-under-$HOME>`.
- **`setup.sh`** (bash, `set -euo pipefail`) is the only entry point for linking/unlinking. It detects the OS via `uname -s` and picks the package list accordingly — that list lives inline in the script (`PACKAGES=(...)` per OS branch), not in a config file. Before stowing it runs `mkdir -p ~/.config ~/.claude`, otherwise Stow's tree folding would symlink the whole directory into the repo on a machine where it doesn't exist yet. It never installs the programs the configs are for (zsh, vim, kitty, claude, jq...): they are listed in `PROGRAMS.md`, and `link` ends by pointing to that file. When a package adds a dependency, add it to `PROGRAMS.md` ("Essentials" when the repo holds its config).
- **ZDOTDIR indirection**: `zsh/.zshenv` sets `ZDOTDIR="$HOME/.config/zsh"`. Stow symlinks `~/.zshenv` and `~/.config/zsh` (the whole `zsh/.config/zsh/` package subtree), so all of `.zshrc`, `alias/`, `functions/`, `plugins/`, `themes/` live under `$ZDOTDIR`. Inside `.zshrc`, `ZSH_HOME=$ZDOTDIR` and everything else (`ZSH_PLUGINS_FOLDER`, `ZSH_THEMES_FOLDER`, etc.) derives from it — don't hardcode a repo path here. Since `~/.config/zsh` is a symlink into the repo, runtime files must not be written under `$ZDOTDIR`: history goes to `${XDG_STATE_HOME:-~/.local/state}/zsh/history` and the completion dump to `${XDG_CACHE_HOME:-~/.cache}/zsh/zcompdump`.
- **Plugins and themes are intentionally NOT vendored in git.** Only the manifest/config that says which plugin or theme to use is tracked (`zsh/.config/zsh/plugins/.zsh_plugins.zsh`, `zsh/.config/zsh/themes/.zsh_theme.zsh`, `zsh/.config/zsh/themes/p10k/.p10k.zsh`). The actual plugin/theme code is cloned on each machine by `./setup.sh link` (`clone_if_missing`, skipped when the directory already exists) and stays gitignored — see the `.gitignore` rules for `/zsh/.config/zsh/plugins/*` and `/zsh/.config/zsh/themes/*` (with explicit exceptions for the tracked manifest files). The same applies to the kitty themes: `kitty/.config/kitty/kitty.conf` includes `./kitty-themes/themes/<name>.conf`, and `setup.sh` clones https://github.com/dexpota/kitty-themes into `~/.config/kitty/kitty-themes` (gitignored as `/kitty/.config/kitty/kitty-themes/`). The eza themes are different: `~/.config/eza` is not a Stow package at all. `setup.sh` (`install_eza_themes`) clones https://github.com/eza-community/eza-themes into `$EZA_CONFIG_DIR/eza-themes` (`.zshrc` exports `EZA_CONFIG_DIR=~/.config/eza`, also on macOS) and creates the `theme.yml` symlink only if missing; the `eza-theme` function (`functions/eza-theme.zsh`) switches it at runtime, so it must never live in the repo. Do not turn plugins/themes into git submodules — this is a deliberate, standing decision.
- **Updates (`functions/update-my-dotfile-config.zsh`)**: `update-my-dotfile-config` runs `git pull --ff-only` in this repo and in every cloned plugin/theme repo. The same file starts a background check on the first prompt (`precmd` hook, so `~/.zsh_local` settings apply and p10k's instant prompt is not disturbed): a process substitution runs `git fetch` in each repo and its output is shown through `zle -F`, so it never blocks the shell. Results go to `${XDG_CACHE_HOME:-~/.cache}/zsh/dotfiles-updates` (reused for `DOTFILES_UPDATE_CHECK_INTERVAL` seconds, default 6h) and git errors to `${XDG_STATE_HOME:-~/.local/state}/zsh/dotfiles-update.log`, both outside `$ZDOTDIR`. Failed checks are reported but never cached. `GIT_TERMINAL_PROMPT=0` and similar git env vars are set only inside that background subshell or as per-command prefixes, never in the interactive shell. The repo list `DOTFILES_UPDATE_REPOS` duplicates the `clone_if_missing` calls in `setup.sh`: when adding a cloned repo, update both. If a third place needs that list, or it grows much longer, centralize it in one shared file.
- **Claude Code (`claude/`)**: only `~/.claude/settings.json`, `~/.claude/CLAUDE.md` and `~/.claude/statusline.sh` are tracked. Everything else in `~/.claude` and `~/.claude.json` is runtime state, caches or account data (including `.credentials.json`) and must never be added; `.gitignore` ignores `/claude/.claude/*` except those three files. Plugins are declared via `enabledPlugins` in `settings.json`, not by copying `~/.claude/plugins/`. `statusline.sh` must keep working on both Linux and macOS: it tries GNU `date -d` and falls back to BSD `date -r`, and needs `jq`.
- **`~/.zsh_local` and `~/.zsh_secrets`** are real files outside the repo, never tracked, never managed by Stow. `.zshrc` creates them (empty, with restrictive permissions) on first run if missing, and sources them last so they can override anything else. Machine-specific config goes in `.zsh_local`; secrets/tokens go in `.zsh_secrets`. The one exception is zoxide: its `eval "$(zoxide init zsh)"` (guarded by `(( $+commands[zoxide] ))`) is the very last block of `.zshrc`, after `.zsh_local`, because zoxide expects to be initialized last (it registers a `chpwd` hook) and reads some `_ZO_*` variables only at init time, so setting them in `.zsh_local` still works. Keep it last when adding new blocks.
- **Stow will refuse to link if a real (non-symlink) file already exists at the target path** (e.g. a pre-existing `~/.zshrc`, `~/.vimrc`, `~/.config/zsh`). `setup.sh` does not attempt automatic backup/removal of conflicting files — that's a manual prerequisite, documented in the README, by design (to avoid risky backup logic in the script).
